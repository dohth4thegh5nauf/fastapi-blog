## 1. Цель и нормативные принципы

**Цель.** Превратить форк в универсальный пакет: Markdown-документы в файлах, настраиваемая схема YAML-frontmatter с экспортом в JSON-LD, проверки целостности; админка и REST API подключаются по желанию. Пакет ничего не знает о своих будущих потребителях.

Нарушение любого принципа считается дефектом.

- **П1. Файловая система — единственный обязательный источник истины.** Базовая установка не требует БД, сессий, админки, брокера или кэш-сервера. Блогом можно полностью управлять правкой файлов в каталоге.
- **П2. Необязательное подключается через extras и ленивые импорты.** `import fastapi_blog` не загружает ничего из админки.
- **П3. Универсальность.** В исходниках, тестах, шаблонах, README и docs нет имён проектов-потребителей и их предметной лексики. Примеры только синтетические (`example.org`, «notes», «articles»). Каждая новая возможность должна быть оправдана для обычного блога.
- **П4. «Не удалось проверить» — отдельный исход, а не успех.** Недоступный внешний инструмент, неразобранный файл, незагруженный контекст дают `undefined` или `unavailable`, но не «ок».
- **П5. Детерминизм.** Экспорт и отчёты не зависят от времени, абсолютных путей и порядка обхода каталога; ключи и документы сортируются стабильно.
- **П6. Обратная совместимость с 0.8.** Публичные имена (`add_blog_to_fastapi`, `setup_fastapi_blog`, `add_admin_to_app`, `add_editor_to_app`, `get_api_router`, `FrontmatterSchema`, `FieldSpec`) и формат файла схемы продолжают работать. Меняется только то, что перечислено ниже как дефект.
- **П7. Без избыточной оптимизации.** Абстракция вводится, когда у неё есть два реальных потребителя. Не вводить: плагинное обнаружение (entry points), слой кэширования, зеркало содержимого в БД, конечные автоматы, DSL.

Удалить `redis[hiredis]` и `pyjwt` полностью: ни зависимости, ни упоминаний, ни пустых заглушек. Кэш владелец добавит сам позже. Отсутствие кэш-сервера ни в каком месте не должно приводить к ошибке или предупреждению.

**3.2 Ленивые импорты.** `fastapi_blog.__init__` не импортирует `admin`. `Admin`, `add_admin_to_app` и `setup_fastapi_blog` доступны через модульный `__getattr__` (PEP 562); при отсутствии extra они поднимают `ImportError` с текстом `pip install "fastapi-blog[admin]"`. Добавить `setup_fastapi_blog(..., admin: bool = True)`: при `admin=False` админка не подключается и extra не нужен.

**3.3 REST API** остаётся в ядре, по умолчанию выключен, зависимостей сверх ядра не требует. Аутентификация подключаемая (см. раздел 7). Сессионная аутентификация работает только если в приложении есть `SessionMiddleware` (extra `admin`); иначе доступны Basic и пользовательская зависимость. Запуск API с `require_auth=True` без настроенных учётных данных или зависимости — ошибка конфигурации при старте, а не анонимная запись.

**3.4 Кэш.** Заменить `lru_cache` в `list_posts` проверкой «подписи каталога»: кортеж `(имя, mtime_ns, size)` файлов; перечитывать при изменении подписи; без TTL; потокобезопасно; без внешних сервисов. Реализация — одна функция в одном модуле, чтобы позже вокруг неё можно было поставить внешний кэш. Протокол или интерфейс кэша не вводить.

**Критерии (A):**

1. В чистом окружении `pip install .` без extras, `python -c "import fastapi_blog"` и запуск тестового приложения с блогом проходят; в `sys.modules` нет `starlette_admin`, `sqlalchemy`, `passlib`, `redis`. Тест с подменой `sys.modules` и CI-матрица «core» / «all extras».
2. Внешняя правка файла видна без перезапуска.
3. `grep -ri redis src pyproject.toml` пуст.

## 4. Хранилище документов (фаза B, в работе)

**Состояние на 0.9.0.** Сделано: 4.1–4.4 и 4.7 (`Collection`, `DocumentStore`, `etag`, `If-Match`, единый разбор и атомарная запись, `safe_document_path` везде). Частично: 4.5 (`on_create` и `read_only` только в REST API; порядок ключей при перезаписи не сохраняется) и 4.6 (`depth` больше 0, теги `{dirname}` и `{filename}`, сахар над двумя `Collection`).

**4.1 Единый модуль** `store.py` (примитивы уже в нём): добавить `DocumentStore` (`list`, `read`, `write`, `delete`, `exists`) на одну `Collection`. Публичная страница, `helpers.list_posts`, REST API и админка используют только его. Две реализации `MarkdownPost` свести к одной поверх `DocumentStore`. `safe_document_path` вызывается везде, где путь строится из slug (включая публичный маршрут).

**4.2 Разбор файла.** Frontmatter — блок между первой строкой `---` в начале файла (допускается BOM) и ближайшей следующей строкой, равной `---` (или `...`). Остальное — тело, байт-в-байт. Файл без открывающего `---` — документ с пустым frontmatter (годен ли он, решает схема). Символы `---` внутри значений YAML и тела на разбор не влияют.

**4.3 Кодировка и запись.** Везде UTF-8, перевод строки `\n`. Запись атомарная: временный файл в том же каталоге плюс `os.replace`. Каталог коллекции создаётся только явным действием создания, но не при чтении.

**4.4 Безопасность путей.** Одна функция проверки slug (шаблон настраивается на коллекцию; по умолчанию как сейчас: строчные буквы, цифры, дефисы, не более 100 символов) и проверка, что итоговый путь после `resolve()` лежит внутри каталога коллекции; символические ссылки наружу не разыменовываются.

**4.5 Целостность данных.** Никаких выдуманных значений: отсутствующая дата остаётся `None` (убрать `datetime.now()`). Поле можно объявить `on_create: today | now | uuid`: значение подставляется только при создании и только если не задано. Неизвестные ключи при `extra: allow` сохраняются при перезаписи; порядок ключей сохраняется. Комментарии YAML при записи через API и админку могут теряться (документировать); ручная правка файлов их не затрагивает.

**4.6 Коллекции.** `Collection(name, dir, schema, slug_pattern=..., extension="md", depth=0, create=True, delete=True)`. Приложение может иметь несколько коллекций с разными схемами (посты, страницы и т. д.). Прежние `posts_dirname` и `pages_dirname` становятся сахаром над двумя коллекциями. Убрать класс-синглтон; `POSTS_DIR` читать как устаревший с предупреждением. Страницы получают схему (по умолчанию прежние поля). Параметры, заимствованные из git-CMS (5.8): `create: false` и `delete: false` запрещают операцию в хранилище, API и админке (для записей, которые не удаляют, а заменяют); `extension` — одно расширение или список (`md`, `markdown`); `depth: N` включает вложенные каталоги глубиной до N (по умолчанию 0, коллекция плоская): slug тогда равен относительному пути без расширения (`a/b/0001-x`), каждый сегмент проверяется шаблоном slug, а в шаблонах доступны `{dirname}` и `{filename}`. В подстановках `validators` (6.2) для вложенной коллекции `{slug}` может содержать `/`; остальные символы по-прежнему из набора `[A-Za-z0-9._:-]`.

**4.7 Конкурентность.** `read` возвращает `etag` (sha256 содержимого). `write` и `delete` принимают `if_match`; несовпадение — `ConflictError` (HTTP 412; 409 при создании существующего). API понимает заголовок `If-Match`; параметр `require_if_match: bool = False`. Запись защищена внутрипроцессной блокировкой на коллекцию (межпроцессную не делать).

**Критерии (B):**

1. Круговой тест `read → write` с таблицей `|---|---|` и `---` в значении YAML — выполнено (`tests/test_store.py`).
2. Параллельная запись двух клиентов с одним `etag` даёт ровно один 412 — реализовано в `DocumentStore` и REST API; проверить покрытие тестом на двух клиентов.
3. Поиск `read_text(` и `write_text(` в `src` не находит вызовов без `encoding`.
4. Все чтения и записи документов идут через `DocumentStore` — выполнено для REST API и админки; остаётся запись админки без валидации по схеме (4.5).
5. Все существующие тесты проходят (базовая линия: 386 тестов в 30 файлах).

## 5. Настраиваемый frontmatter и JSON-LD (фаза C — главный раздел)

**5.1 Расширение `FieldSpec`.** Все новые опции необязательны, доступны и в YAML/JSON-файле схемы. Ошибки схемы выявляются при её загрузке с указанием поля (как сейчас).

| Опция | Смысл |
| --- | --- |
| `label`, `hint` | Подпись и подсказка поля для админки и сообщений `check`; по умолчанию `label` равен имени поля |
| `choices: [...]` | Допустимые значения; элемент — скаляр или `{value, label}` (`label` только для UI, сохраняется `value`); для `list[str]` проверяется каждый элемент |
| `pattern` | Строка-regex или пара `[regex, "сообщение об ошибке"]`; полное совпадение (`re.fullmatch`); для списков — `item_pattern` для элементов. Regex компилируется при загрузке схемы |
| `min`, `max` | Границы значения для `int` и `float` |
| `min_items`, `max_items` | Границы длины списка; каждая работает сама по себе (в git-CMS `min`/`max` списка действуют только вместе) |
| `type: link`, `list[link]` | Ссылка на другой документ, см. 5.1.1 (MUST) |
| `type: object`, `list[object]` | Вложенные поля `fields`, см. 5.1.2 (SHOULD) |
| `type: file`, `image` | Путь к файлу строкой, см. 5.1.3 (SHOULD) |
| `hidden: true` | Поле не показывается в админке; удобно вместе с `default` и `on_create` |
| `read_only: true` | Хранилище отклоняет изменение значения у существующего документа (через API и админку); нужно для стабильных идентификаторов |
| `on_create` | `today`, `now` или `uuid` (для `uuid` — необязательный `prefix`); значение подставляется один раз при создании и только если не задано, см. 4.5 |
| `description` | Уже есть; попадает в JSON Schema (5.7) |

**5.1.1 Ссылки (`link`, MUST).** Опции поля: `collection` — целевая коллекция (по умолчанию та же); `value_field` — поле целевого документа, значение которого хранится в ссылке (по умолчанию поле с alias `@id`, если оно есть, иначе `slug`); `filters` — список `{field, values}`: ссылка допустима только на документы, у которых поле принимает одно из значений (для списка достаточно одного совпадения). Это подсказка для автодополнения в админке и правило целостности для `check`: ссылка на несуществующий документ и ссылка на документ вне фильтра — разные находки. Абсолютные IRI вне коллекции пропускаются. Отдельного индекса нет: ссылки разрешаются по файлам коллекции.

**5.1.2 Вложенные поля (SHOULD).** Тип `object` задаёт вложенные `fields` (те же опции, рекурсивно), `list[object]` — повторяющиеся блоки. Глубина вложенности не больше 3, иначе ошибка схемы. В JSON-LD вложенный объект становится вложенным узлом; его `@id` и `@type` задаются через `alias` внутри `fields`. Списки с разными наборами полей для разных элементов не поддерживаются.

**5.1.3 Файлы (SHOULD).** Типы `file` и `image` хранят путь строкой. Опции: `media_dir` (каталог файлов относительно корня проекта) и `public_path` (префикс публичного пути, по умолчанию совпадает с `media_dir`); в поле записывается публичный путь. `check.files: off|warn|error` (по умолчанию `off`) сообщает о ссылке на отсутствующий файл. Загрузка файлов через админку, обработка изображений и медиатеки вне объёма: файлы кладут в каталог руками, как и документы. Имена опций намеренно не повторяют `media_folder` и `public_folder` из git-CMS: в проекте не используют слово «folder» (`AGENTS.md`).

**5.2 Ключи JSON-LD.** Ключи `@id`, `@type`, `@context` задаются через существующий `alias`, например `FieldSpec("doc_id", alias="@id")`. Ключи с `@` должны корректно читаться и записываться (в YAML их обязательно брать в кавычки; сериализатор ставит кавычки сам), это покрывается круговым тестом. Ключ `@context` в документе допустим как поле типа `dict` или `any` и переопределяет контекст схемы для этого документа.

**5.3 Секция `jsonld` файла схемы.** Необязательна: без неё JSON-LD-функции выключены. Синтетический пример:

```yaml
version: 1
extra: forbid
fields:
  id:       {alias: "@id", read_only: true, pattern: ["note:[0-9]{4}", "Expected note:NNNN"]}
  kind:     {alias: "@type", default: Note, hidden: true}
  title:    {required: true, role: title, max_length: 200}
  status:   {required: true, choices: [draft, active, retired], hint: "Lifecycle state"}
  date:     {type: date, role: date, on_create: today}
  replaces: {type: "list[link]", collection: notes, value_field: id}
  related:  {type: "list[link]", collection: notes, value_field: id,
             filters: [{field: status, values: [active]}], max_items: 5}
  tags:     {type: "list[str]", role: tags}
jsonld:
  context:                    # inline, путь к файлу в проекте или список
    "@vocab": "https://example.org/vocab#"
    note: "https://example.org/notes/"
    replaces: {"@id": "https://example.org/vocab#replaces", "@type": "@id"}
    related:  {"@id": "https://example.org/vocab#related",  "@type": "@id"}
    date: {"@id": "https://example.org/vocab#date", "@type": "http://www.w3.org/2001/XMLSchema#date"}
  base: "https://example.org/"
  id: "{base}{collection}/{slug}"   # шаблон (язык шаблонов — 6.4); используется, если нет поля с alias @id
  type: Note                        # @type по умолчанию
  content_term: null                # термин для тела документа; null — не выводить
```

И документ к нему:

```markdown
---
"@id": note:0007
"@type": Note
title: Use plain files
status: active
date: 2026-10-01
replaces: [note:0003]
tags: [storage]
---
Body text.
```

**5.4 Эмиссия.** Документ превращается в объект JSON-LD по правилам:

- ключи — внешние (`alias`), значения — из проверенной модели; `None` и пустые значения не выводятся;
- `@context` берётся из схемы (или из документа); `@id` — значение поля с alias `@id`, иначе по шаблону `jsonld.id`; `@type` — поле с alias `@type`, иначе `jsonld.type`;
- тело выводится только при заданном `content_term` (Markdown как есть, HTML не выводится);
- даты в ISO 8601; порядок ключей: `@context`, `@id`, `@type`, затем по порядку схемы; никаких времён генерации, абсолютных путей и номеров строк.

Интерфейсы:

- Python: `document_to_jsonld(doc, collection) -> dict`, `collection_to_jsonld(collection) -> dict` (`@graph`, документы отсортированы по `@id`, затем по slug).
- HTTP (включается `jsonld_routes=True`, по умолчанию выключено): `GET {prefix}/{slug}.jsonld` и `GET {prefix}/index.jsonld`, `Content-Type: application/ld+json`; публичный вывод содержит только опубликованные документы.
- CLI: `python -m fastapi_blog export --collection NAME --format jsonld [--out FILE]`. С extra `jsonld` доступны также `--format expanded` и `--format nquads` (через `pyld`; вывод сортирован, пригоден для `git diff`).

**5.5 Контекст и безопасность.** По умолчанию контекст берётся только из inline-описания или файла внутри корня проекта. Удалённые контексты запрещены; включаются явным `allow_remote_contexts: [список URL]` и только при установленном extra `jsonld` (таймаут, лимит размера, без редиректов на другие хосты). Лимиты размера контекста и числа документов в `@graph` настраиваются. Ничего из контекста не исполняется.

**5.6 Контроль «потерянных терминов».** При разворачивании JSON-LD молча отбрасывает ключи, не определённые в контексте. Поэтому `check` (раздел 6) сообщает о ключе схемы, не покрытом контекстом ни термином, ни префиксом, ни `@vocab` (`strict_context: error`, `warn` или `off`, по умолчанию `error`). Статическая проверка (без `pyld`) разбирает inline или локальный контекст; при наличии `pyld` дополнительно разворачивается пробный документ. Контекст, который нельзя загрузить, даёт `undefined`, а не «ок».

**5.7 Дополнительно (SHOULD).**

- `python -m fastapi_blog schema --json-schema` печатает JSON Schema frontmatter из Pydantic-модели (`choices` → `enum`, `pattern`, описания).
- Роль `status` как обобщение `published`: список `published_values` в схеме определяет, какие документы публичны; одновременное задание ролей `published` и `status` — ошибка схемы.

**Критерии (C):**

1. Синтетическая коллекция из 5.3 (файлы `notes/0001-….md`) создаётся только файлами, `check` проходит.
2. Неверный `status`, неподходящий `@id` и поле вне контекста дают три отдельные диагностики.
3. Экспорт детерминирован: два запуска дают одинаковые байты, порядок файлов в ФС не влияет.
4. Круговой тест ключей с `@`.
5. Существующие схемы из `tests/examples` работают без изменений.

**Критерии (C), дополнение:**

- `pattern` с сообщением выводит это сообщение в диагностике; `choices` с `{value, label}` принимает только `value`.
- Ссылка на несуществующий документ и ссылка на документ вне `filters` дают две разные диагностики; значение поля с `read_only` нельзя изменить через хранилище.
- `on_create: uuid` даёт одно и то же значение при повторных сохранениях.
- `list[object]` глубиной больше 3 отвергается при загрузке схемы; вложенный объект даёт вложенный узел в JSON-LD.
- `check.files: error` находит ссылку на отсутствующий файл.

**5.8 Что заимствовано из git-CMS и что нет.** Ориентир — Decap CMS: одна YAML-конфигурация, из которой строятся форма и проверки, подтверждает выбранную схему работы. «Взять» означает реализовать универсальную опцию без привязки к git-хостингу.

| Идея git-CMS | Решение | Где |
| --- | --- | --- |
| Один декларативный файл настроек, из него строятся форма и проверки | Уже так: схема и коллекции; админка строится из схемы | 5, 7 |
| `label`, `hint`, `pattern` с текстом ошибки | Взять | 5.1 |
| Виджет select: значения или `{label, value}`, `multiple`, `min`/`max` | Взять как `choices`, `min_items`, `max_items` | 5.1 |
| Виджет relation: `collection`, `value_field`, `filters` | Взять как `link`; фильтры работают и как правило целостности | 5.1.1 |
| Виджеты object и list с `fields` | Взять ограниченно: глубина до 3, без вариативных типов | 5.1.2 |
| Виджет uuid: значение создаётся один раз, `prefix`, только чтение | Взять как `on_create: uuid` и `read_only`: `@id` не зависит от имени файла и заголовка | 5.1 |
| Виджет hidden, `default`; datetime с текущим временем по умолчанию | `hidden` взять; время подставляется только по явному `on_create` (в самом git-CMS неявное «сейчас» по умолчанию убрали в 3.2.1) | 4.5 |

| Шаблоны slug: теги полей и дат, фильтры, `encoding`, `clean_accents`; файл создаётся один раз и не переименовывается | Взять; перегруженный тег `slug` (в разных шаблонах значит разное) не повторять: у нас `slug` и `title_slug` | 6.4 |
| `summary` — подпись документа в списке | Взять | 6.4 |
| Санитизация превью (в 3.13 включена по умолчанию как защита от XSS) | Взять: превью в админке санитизируется по умолчанию | 7 |
| Поля file и image | Взять только строковый тип и проверку существования файла | 5.1.3 |
| Медиатеки, загрузки, обработка изображений | Не брать | — |
| Редакционный процесс на ветках и PR, шаблоны коммитов, открытое авторство, бэкенды git-хостингов | Не брать в ядро: пакет не знает о git; хост подключает `on_change` (6.5) и сам делает коммит или PR | 6.5 |
| i18n, сортировка и фильтры списков, поиск, `preview_path`, заметки, пользовательские виджеты | Не брать (нет второго потребителя, П7) | — |
| TOML и JSON frontmatter, файловые коллекции | Не брать сейчас; только YAML-frontmatter | — |

**5.9 SEO-расширение frontmatter.** Пункты 5.9.1–5.9.3 и 5.9.6 — MUST, остальное — SHOULD или MAY.

**5.9.0 Принципы.**

- SEO — не отдельная подсистема, а несколько новых семантических ролей схемы (как `title`, `date`, `description`) плюс настройки сайта. Роль привязывается к полю схемы; имя поля и `alias` выбирает автор схемы.
- Если роль не привязана и настройка не задана, поведение прежнее (П6). Исключения-исправления перечислены в 5.9.6.
- Только то, что поисковики используют: `<meta name="keywords">`, `priority` и `changefreq` в sitemap не поддерживаются (по публичной документации Google они не учитываются). Теги документа попадают только в `article:tag` и в `keywords` структурированных данных.
- Универсальность (П3): в пакете нет имён сайтов, авторов и соцсетей; все значения приходят из frontmatter и настроек.

**5.9.1 Новые роли.** Роль привязывается к одному полю, как остальные (`ROLES` и `_ROLE_TYPES` в `models/schema.py`).

| Роль | Тип поля | Назначение |
| --- | --- | --- |
| `seo_title` | `str` | Заголовок для `<title>`, `og:title`, `twitter:title`; если не задан — `title` |
| `description` (уже есть) | `str` | `<meta name="description">`, `og:description`, `twitter:description`, `description` в структурированных данных |
| `canonical` | `str` | Явный канонический адрес: абсолютный `https://` или путь от корня сайта; иначе адрес вычисляется (5.9.4) |
| `robots` | `list[str]` | Директивы `<meta name="robots">`; допустимы `noindex`, `nofollow`, `noarchive`, `nosnippet` (проверяются как `choices`) |
| `image` | `str` | Картинка для `og:image`, `twitter:image` и структурированных данных: путь внутри сайта или абсолютный URL |
| `image_alt` | `str` | `og:image:alt`, `twitter:image:alt`; при заданном `image` обязателен (находка `check`, 5.9.7) |
| `updated` | `str`, `date` или `datetime` | Время изменения: `article:modified_time`, `dateModified`, `lastmod` в sitemap; если не задано — `date` |
| `author` | `str` или `list[str]` | `<meta name="author">` и `author` в структурированных данных; если не задано — `seo.default_author` |
| `lang` | `str` | Язык документа (код BCP 47): `<html lang>`, `og:locale`, `inLanguage`; если не задан — язык интерфейса запроса |
| `redirect_from` | `list[str]` | Прежние адреса документа (5.9.5) |

**Готовый набор полей.** `fastapi_blog.seo.seo_fields()` возвращает `FieldSpec` для этих ролей (`choices` у `robots`, подписи `label` и `hint`). Автор схемы добавляет набор целиком или частично и может переименовать поля. Длины `seo_title` и `description` ограничиваются не схемой, а проверкой `check` (5.9.7): превышение рекомендуемой длины — предупреждение, а не отказ записи.

**5.9.2 Настройки сайта (`SeoConfig`).** Секция `seo:` файла схемы (по образцу `jsonld:`) и параметр `seo=` у `add_blog_to_fastapi` и `setup_fastapi_blog`; параметр сильнее секции. Ошибки значений выявляются при загрузке схемы с именем ключа.

```yaml
seo:
  site_url: "https://example.org"      # база абсолютных адресов; в продакшене задавать всегда
  site_name: "Example Notes"
  title_template: "{title} - {site_name}"
  default_image: "/static/social.png"
  default_author: null
  default_robots: []
  index_description: "Short site description"
  og: true
  twitter_card: summary_large_image    # summary, summary_large_image или null
  structured_data: blogposting         # blogposting, article или none
  description_fallback: excerpt        # excerpt или none
  description_length: 160
  noindex_tags: false                  # страницы тегов получают robots noindex
```

Без секции и без параметра включены только исправления 5.9.6 (описание и `lang`). С секцией (даже пустой, `seo: {}`) работает всё из 5.9.4, но тег выводится только если у него есть значение. Без `site_url` абсолютные адреса строятся из URL запроса (как сейчас). Язык шаблонов `title_template` — из 6.4; до его появления допустим `str.format` с теми же именами.

**5.9.3 Порядок подстановки значений.**

| Значение | Источники по порядку |
| --- | --- |
| Заголовок | `seo_title`, затем `title`; к результату применяется `title_template`; пусто — `site_name`; иначе тег не выводится |
| Описание | Поле `description`; при `description_fallback: excerpt` — первые `description_length` символов простого текста тела (без Markdown и HTML, обрезка по границе слова, детерминированно); для главной и списков — `index_description`; иначе тег не выводится |
| Канонический адрес | Поле `canonical`, затем вычисленный адрес (как сейчас: без query, с учётом локали) |
| Картинка | `image`, затем `default_image` |
| Время изменения | `updated`, затем `date` |
| Автор | `author`, затем `default_author` |
| Robots | Объединение поля `robots` и `default_robots` без дублей, порядок стабилен |
| Язык | `lang`, затем язык интерфейса запроса |

**5.9.4 Вывод в страницу.**

- Фрагмент `partials/_seo_head.html` подключается из `layouts/base.html` и переопределяется так же, как остальные шаблоны. Значения собирает Python-функция `seo.build_head(...)`, шаблон их только печатает.
- Экранирование HTML автоматическое (Jinja). `canonical` и `image` принимаются только как `http`/`https` или путь от корня сайта; другое значение отбрасывается, а `check` сообщает об ошибке.
- Абсолютные адреса строятся от `site_url`. Если он задан, заголовок `Host` запроса в адресах не используется.
- Теги: `<title>`, `<meta name="description">`, `<link rel="canonical">`, `<meta name="robots">`, `<meta name="author">`; Open Graph (`og:title`, `og:description`, `og:type` — `article` для документов и `website` для главной и списков, `og:url`, `og:image`, `og:image:alt`, `og:site_name`, `og:locale`, `article:published_time`, `article:modified_time`, `article:tag`); Twitter (`twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`, `twitter:image:alt`).
- Структурированные данные: `<script type="application/ld+json">` с типом `BlogPosting` (или `Article`) в словаре schema.org: `headline`, `description`, `image`, `datePublished`, `dateModified`, `author` (`Person` с `name`), `inLanguage`, `mainEntityOfPage` (канонический адрес), `keywords` (из тегов). Это отдельный генератор: он не связан с экспортом `document_to_jsonld`, где словарь задаёт автор схемы. При встраивании в страницу в JSON экранируются `<`, `>` и `&` (`\u003c` и т. д.), чтобы значение не могло закрыть тег `script`.
- Заголовок `Link: <…>; rel="canonical"` (уже есть) использует тот же адрес, включая переопределение из поля. Страница, у которой `canonical` указывает на другой адрес, не получает `hreflang` (как и прочие дубли).

**5.9.5 Sitemap, robots.txt и редиректы (SHOULD).** Включаются параметром `seo_routes=True`, по умолчанию выключены: эти адреса часто принадлежат хосту.

- `GET /sitemap.xml`: только опубликованные документы; исключаются документы с `noindex` в `robots` и документы, у которых `canonical` указывает на другой адрес. `<loc>` — канонический абсолютный адрес, `<lastmod>` — `updated` или `date` (формат W3C), без `priority` и `changefreq`; порядок по `loc`, вывод детерминирован. Главная и список постов включаются, страницы тегов — если `noindex_tags: false`. Если адресов больше 50 000 (лимит протокола), выдаётся индекс карт (`sitemap-1.xml` и далее).
- `GET /robots.txt`: `User-agent: *`, `Allow: /` (или список `disallow` из настроек) и строка `Sitemap:` с абсолютным адресом. Включение `seo_routes=True` без `site_url` — ошибка конфигурации при старте (как `ConfigurationError` для API без учётных данных).
- `redirect_from`: старый адрес (slug или путь) отвечает постоянным редиректом `301` на текущий канонический адрес документа. Индекс старых адресов строится при загрузке коллекции с тем же кэшем по подписи каталога. Неопубликованные документы редиректов не создают.

**5.9.6 Исправление существующего поведения (MUST, записать в `CHANGELOG.md`).**

- У `<html>` нет атрибута `lang`: добавить (порядок подстановки — 5.9.3).
- Роль `description` не выводилась в `<meta name="description">`: выводить.

**5.9.7 Проверки `check` (SHOULD).** Находки с настраиваемым уровнем, секция `seo.check`: `title_max` (по умолчанию 60), `description_max` (160), `missing_description` (`warn`), `missing_image` (`off`), `duplicate_title` и `duplicate_description` (`warn`, сравнение внутри коллекции), `image_alt_required` (`error`). Числа — ориентиры, а не требования поисковиков (сниппеты усекаются по ширине в пикселях, а не по числу символов), поэтому превышение по умолчанию только предупреждение. Всегда `error`: `canonical` не `http`/`https` и не путь; `robots` с неизвестной директивой; `image` указывает на несуществующий файл (при `check.files`, 5.1.3); конфликты `redirect_from` (старый адрес совпадает со slug существующего документа, один адрес у двух документов, цепочки и петли). Диагностика детерминирована.

**Критерии (5.9):**

## 6. Проверки и CLI (фаза D)

**6.1 `python -m fastapi_blog check [--collection NAME] [--json] [--fail-on error|warning]`.** Проверяет: разбор файла, схему, дубликаты уникальных ключей (6.4), ссылки (`check.links: off|warn|error`, по умолчанию `off`; ссылка разрешается по полю с alias `@id` или по slug в той же коллекции; абсолютные IRI вне коллекции пропускаются), контекст (5.6), внешние проверки (6.2). Коды выхода: `0` — чисто; `1` — есть находки уровня не ниже `--fail-on` (по умолчанию `error`); `2` — находок нет, но что-то нельзя было проверить (`undefined`); `64` — ошибка использования или конфигурации. `undefined` никогда не сводится к «чисто», но находка приоритетнее неопределённости. Вывод детерминирован; `--json` — машинный формат.

**6.2 Внешние проверки (`validators`).** В конфигурации коллекции — список проверок: Python-callable `(doc, ctx) -> list[Issue]` или команда.

```yaml
validators:
  - name: lint
    argv: ["markdownlint", "{path}"]       # список, без shell
    exit_map: {0: ok, 1: error, 2: undefined}
    unavailable: undefined                 # команда не найдена или таймаут
    timeout: 20
    blocking: [error, undefined]           # что блокирует запись через API и админку
```

Подстановки: `{path}` (формирует хранилище: путь файла относительно корня проекта), `{slug}`, `{collection}` и `{fields.NAME}` (скалярное поле frontmatter). Значения `{slug}`, `{collection}`, `{fields.NAME}` обязаны соответствовать `[A-Za-z0-9._:-]+`, иначе проверка завершается ошибкой и команда не запускается. Запуск без shell, `cwd` — корень проекта, окружение — белый список, вывод ограничен по размеру и попадает в диагностику как текст. Команды берутся только из конфигурации, никогда из запроса.

**6.3 Запись с проверкой.** Для API и админки: под блокировкой коллекции записать новый вариант, выполнить блокирующие проверки на результате; при блокирующем исходе вернуть прежнее содержимое (или удалить созданный файл) и ответить HTTP 422 с телом `issues`. Ограничение (документировать): промежуточное состояние на диске видно другим читателям; проверка во временной копии вне этого ТЗ.

**6.4 Шаблоны, slug и нумерация.** Один язык шаблонов для `slug_template`, `jsonld.id`, `summary` и подстановок в `validators`: `{имя}`, `{fields.имя}` (явная форма, если имя поля совпадает со служебным тегом) и цепочка фильтров `{имя|фильтр(арг)}`. Фильтры: `lower`, `upper`, `truncate(n)`, `default(x)`, `pad(n)` (дополнить нулями слева), `date(формат)`. Служебные теги: `slug` — полный slug документа (имя файла без расширения; для вложенных коллекций относительный путь), `title_slug` — безопасная форма поля с ролью `title`, `seq` — номер (см. ниже), `year`, `month`, `day` — по полю с ролью `date`, а если его нет или оно пусто — по времени первого сохранения (UTC), `dirname`, `filename`, `collection`. Выражения не вычисляются; неизвестный тег — ошибка конфигурации при загрузке.

Параметры slug коллекции: `slug.encoding` (`unicode` по умолчанию или `ascii`), `slug.clean_accents` (bool), `slug.sanitize_replacement` (по умолчанию `-`); имя файла сокращается до 200 байт. Slug создаётся один раз при первом сохранении и не меняется при правке заголовка или даты; переименование — отдельная явная операция.

Нумерация (SHOULD): `slug_template: "{seq|pad(4)}-{title_slug}"` и `unique: [seq]`. Следующий номер вычисляется под блокировкой по существующим именам файлов (регулярное выражение выводится из шаблона); второй документ с тем же `seq` — конфликт. Для файлов, созданных вручную, дубликаты находит `check`.

`summary: "{status} · {title}"` задаёт подпись документа в списке админки и в человекочитаемом выводе `check`; по умолчанию — поле с ролью `title`.

**6.5 Событие изменения (MAY).** Хук `on_change(event)` (`created`, `updated`, `deleted`; slug, etag, пользователь) без хранения журнала.

**Критерии (D):** коды выхода `0/1/2/64` покрыты тестами; внешняя команда даёт исходы `ok`, `error`, `undefined`, `unavailable`, включая таймаут; значение вроде `a;rm` в подстановке отклоняется, команда не запускается; блокирующий исход возвращает файл в прежнее состояние.

## 7. Админка и безопасность (extra `admin`, фаза E)

1. `authorize(request, resource, action) -> bool` — единая точка проверки прав. Строится поверх контракта starlette-admin 1.0 (`AuthProvider.authenticate(request)` возвращает `AdminUser` или `None`) и используется во всех представлениях админки (имена флагов прав сверить с версией 1.0.3) и в REST API. По умолчанию — запрет. Функцию можно заменить своей. Сейчас `has_permission` определён в `admin/rbac_auth_provider.py`, но нигде не применяется.
2. Роли `admin`, `editor`, `viewer` реально применяются. Тест: `viewer` не может записать ни через админку, ни через API (403); тест выполняется на starlette-admin 1.0.3.
3. Нет учётных данных по умолчанию: без заданных пароля и секрета сессии `add_admin_to_app` и `setup_fastapi_blog` поднимают ошибку конфигурации. Сейчас `admin` / `Admin123!` подставляются в `__init__.py`, `admin/__init__.py` и `admin/auth_provider.py` (режим `admin=False` их уже не подставляет). Явный `insecure_dev=True` возвращает прежнее поведение с громким предупреждением. Слабый секрет (короче 32 символов или из списка известных) без `insecure_dev` — ошибка, а не предупреждение.
4. Сравнение Basic-пароля через `secrets.compare_digest` уже сделано (фаза A). Остаётся: cookie сессии с `SameSite=Lax` как минимум, настраиваемый `https_only`, проверка `Origin` и `Host` у записи с cookie. В starlette-admin 1.0 у `Admin(...)` есть собственные CSRF и flash cookie: не дублировать их, а проверить, что запись через REST API с сессионной cookie защищена так же.
5. Заменить `passlib` (не поддерживается с 2020 года, из-за него закреплён `bcrypt<4.1`) на прямое использование `bcrypt` или другой поддерживаемый хэшер и снять закрепление. Тесты: хэширование и проверка, пароль длиннее 72 байт, уже сохранённые хэши продолжают проходить проверку (`tests/test_password_validation.py`).
6. Админка сохраняет через сервисный слой напрямую (без HTTP-вызова собственного API). Форма строится из схемы: `label` и `hint` — подписи, `choices` — select, `pattern` — валидация с текстом ошибки, `link` — автодополнение по целевой коллекции с учётом `filters`, `object` и `list[object]` — вложенные группы полей; поля с `hidden` не показываются, с `read_only` не редактируются после создания. Форма показывает диагностику проверок и конфликт `etag`.
7. Превью разметки в админке санитизируется по умолчанию так же, как публичный рендер; отключается только явной опцией. Проверить текущее поведение и покрыть тестом с `<script>` в теле документа.
8. Страницы ролей и пользователей уже используют единую тему и переключатель языка (admin/templates/layout.html); новых требований к теме нет.
9. Показ диффа перед сохранением и история изменений — вне объёма (MAY).

**Критерии (E):** тесты прав на все роли и действия; запуск без пароля падает с понятной ошибкой; форма для схемы из 5.3 показывает select для `status`.
