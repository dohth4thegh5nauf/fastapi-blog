# ТЗ: fastapi-blog 0.9 — файловая CMS с настраиваемым frontmatter и JSON-LD

Для агента-разработчика · 2026-10-29 · база: форк pydanny/fastapi-blog, версия 0.8.0

## 1. Цель и нормативные принципы

**Цель.** Превратить форк в универсальный пакет: Markdown-документы в файлах, настраиваемая схема YAML-frontmatter с экспортом в JSON-LD, проверки целостности; админка и REST API подключаются по желанию. Пакет ничего не знает о своих будущих потребителях.

Нарушение любого принципа считается дефектом.

- **П1. Файловая система — единственный обязательный источник истины.** Базовая установка не требует БД, сессий, админки, брокера или кэш-сервера. Блогом можно полностью управлять правкой файлов в каталоге.
- **П2. Необязательное подключается через extras и ленивые импорты.** `import fastapi_blog` не загружает ничего из админки.
- **П3. Универсальность.** В исходниках, тестах, шаблонах, README и docs нет имён проектов-потребителей и их предметной лексики. Примеры только синтетические (`example.org`, «notes», «articles»). Каждая новая возможность должна быть оправдана для обычного блога.
- **П4. «Не удалось проверить» — отдельный исход, а не успех.** Недоступный внешний инструмент, неразобранный файл, незагруженный контекст дают `undefined` или `unavailable`, но не «ок».
- **П5. Детерминизм.** Экспорт и отчёты не зависят от времени, абсолютных путей и порядка обхода каталога; ключи и документы сортируются стабильно.
- **П6. Обратная совместимость с 0.8.** Публичные имена (`add_blog_to_fastapi`, `setup_fastapi_blog`, `add_admin_to_app`, `add_editor_to_app`, `get_api_router`, `FrontmatterSchema`, `FieldSpec`) и формат файла схемы продолжают работать. Меняется только то, что перечислено ниже как дефект.
- **П7. Без избыточной оптимизации.** Абстракция вводится, когда у неё есть два реальных потребителя. Не вводить: плагинное обнаружение (entry points), слой кэширования, зеркало содержимого в БД, конечные автоматы, DSL.

## 2. Состояние кода (проверено по 0.8.0)

- `pyproject.toml`: все зависимости обязательны, включая `starlette-admin[i18n]`, `sqlalchemy[asyncio]`, `aiosqlite`, `itsdangerous`, `pyjwt`, `passlib[bcrypt]`, `python-multipart`, `redis[hiredis]`. `redis` и `jwt` в `src/` не используются.
- `fastapi_blog/__init__.py` на верхнем уровне импортирует `.admin`; `setup_fastapi_blog()` всегда ставит и блог, и админку и подставляет учётные данные по умолчанию (`admin` / `Admin123!`).
- Три независимые реализации чтения и записи документа: `helpers.list_posts`, `editor._parse_file` / `_serialize`, `admin/markdown_model.MarkdownPost`. Разбор в `helpers` делает `split("---")` по всему тексту, а `load_content_from_markdown_file` склеивает тело через `"\n---\n"` и портит любую `---` внутри текста (например, `|---|---|` в таблице).
- `read_text()` и `write_text()` вызываются без `encoding`.
- `MarkdownPost` хранит каталог в атрибуте класса; админка читает `POSTS_DIR` из окружения; форма сохраняет HTTP-вызовом `/api/posts/save` с зашитым URL. Если даты нет, подставляется `datetime.now()`.
- `list_posts` под `lru_cache` сбрасывается только записью через API: внешние правки файлов не видны до перезапуска.
- `Role.has_permission` нигде не вызывается; REST API проверяет только наличие сессии.
- Схема (`models/schema.py`): типы `str/int/float/bool/datetime/date/list[str]/list[int]/dict/any`; роли `title/date/published/tags/description`; нет перечислений, шаблонов, ссылок; страницы (`pages/`) вне схемы. Docstring `add_blog_to_fastapi` утверждает, что админка схему не использует, а `docs/FRONTMATTER_SCHEMA.md` — что использует: привести к фактическому поведению.

## 3. Пакеты, импорты, кэш (фаза A)

**3.1 Состав зависимостей.** Ядро — набор исходного проекта: `fastapi`, `jinja2`, `jinja2-time`, `markdown`, `nh3`, `pydantic`, `pyyaml`, `pymdown-extensions`, `uvicorn` (сверить через `git diff upstream/main -- pyproject.toml`). Extras:

- `admin`: `starlette-admin[i18n]`, `sqlalchemy[asyncio]`, `aiosqlite`, `itsdangerous`, `passlib[bcrypt]`, `python-multipart`.
- `jsonld`: `pyld` (только для разворачивания и N-Quads, см. 5.4).
- `dev`: как сейчас.

Удалить `redis[hiredis]` и `pyjwt` полностью: ни зависимости, ни упоминаний, ни пустых заглушек. Кэш владелец добавит сам позже. Отсутствие кэш-сервера ни в каком месте не должно приводить к ошибке или предупреждению.

**3.2 Ленивые импорты.** `fastapi_blog.__init__` не импортирует `admin`. `Admin`, `add_admin_to_app` и `setup_fastapi_blog` доступны через модульный `__getattr__` (PEP 562); при отсутствии extra они поднимают `ImportError` с текстом `pip install "fastapi-blog[admin]"`. Добавить `setup_fastapi_blog(..., admin: bool = True)`: при `admin=False` админка не подключается и extra не нужен.

**3.3 REST API** остаётся в ядре, по умолчанию выключен, зависимостей сверх ядра не требует. Аутентификация подключаемая (см. раздел 7). Сессионная аутентификация работает только если в приложении есть `SessionMiddleware` (extra `admin`); иначе доступны Basic и пользовательская зависимость. Запуск API с `require_auth=True` без настроенных учётных данных или зависимости — ошибка конфигурации при старте, а не анонимная запись.

**3.4 Кэш.** Заменить `lru_cache` в `list_posts` проверкой «подписи каталога»: кортеж `(имя, mtime_ns, size)` файлов; перечитывать при изменении подписи; без TTL; потокобезопасно; без внешних сервисов. Реализация — одна функция в одном модуле, чтобы позже вокруг неё можно было поставить внешний кэш. Протокол или интерфейс кэша не вводить.

**Критерии (A):**

1. В чистом окружении `pip install .` без extras, `python -c "import fastapi_blog"` и запуск тестового приложения с блогом проходят; в `sys.modules` нет `starlette_admin`, `sqlalchemy`, `passlib`, `redis`. Тест с подменой `sys.modules` и CI-матрица «core» / «all extras».
2. Внешняя правка файла видна без перезапуска.
3. `grep -ri redis src pyproject.toml` пуст.

## 4. Хранилище документов (фаза B)

**4.1 Единый модуль** `store.py`: `DocumentStore` (`list`, `read`, `write`, `delete`, `exists`) на одну `Collection`. Блог, REST API и админка используют только его. Три прежние реализации удалить.

**4.2 Разбор файла.** Frontmatter — блок между первой строкой `---` в начале файла (допускается BOM) и ближайшей следующей строкой, равной `---` (или `...`). Остальное — тело, байт-в-байт. Файл без открывающего `---` — документ с пустым frontmatter (годен ли он, решает схема). Символы `---` внутри значений YAML и тела на разбор не влияют.

**4.3 Кодировка и запись.** Везде UTF-8, перевод строки `\n`. Запись атомарная: временный файл в том же каталоге плюс `os.replace`. Каталог коллекции создаётся только явным действием создания, но не при чтении.

**4.4 Безопасность путей.** Одна функция проверки slug (шаблон настраивается на коллекцию; по умолчанию как сейчас: строчные буквы, цифры, дефисы, не более 100 символов) и проверка, что итоговый путь после `resolve()` лежит внутри каталога коллекции; символические ссылки наружу не разыменовываются.

**4.5 Целостность данных.** Никаких выдуманных значений: отсутствующая дата остаётся `None` (убрать `datetime.now()`). Поле можно объявить `on_create: today | now`: значение подставляется только при создании и только если не задано. Неизвестные ключи при `extra: allow` сохраняются при перезаписи; порядок ключей сохраняется. Комментарии YAML при записи через API и админку могут теряться (документировать); ручная правка файлов их не затрагивает.

**4.6 Коллекции.** `Collection(name, dir, schema, slug_pattern=..., glob="*.md")`. Приложение может иметь несколько коллекций с разными схемами (посты, страницы и т. д.). Прежние `posts_dirname` и `pages_dirname` становятся сахаром над двумя коллекциями. Убрать класс-синглтон; `POSTS_DIR` читать как устаревший с предупреждением. Страницы получают схему (по умолчанию прежние поля).

**4.7 Конкурентность.** `read` возвращает `etag` (sha256 содержимого). `write` и `delete` принимают `if_match`; несовпадение — `ConflictError` (HTTP 412; 409 при создании существующего). API понимает заголовок `If-Match`; параметр `require_if_match: bool = False`. Запись защищена внутрипроцессной блокировкой на коллекцию (межпроцессную не делать).

**Критерии (B):**

1. Круговой тест `read → write` без изменений даёт идентичный файл (кроме нормализации заголовка, 4.5); в теле таблица `|---|---|`, в значении YAML есть `---`.
2. Параллельная запись двух клиентов с одним `etag` даёт ровно один 412.
3. `rg "read_text\(\)|write_text\(" src` не находит вызовов без `encoding`.
4. Три старые реализации удалены, все существующие тесты проходят.

## 5. Настраиваемый frontmatter и JSON-LD (фаза C — главный раздел)

**5.1 Расширение `FieldSpec`.** Все новые опции необязательны, доступны и в YAML/JSON-файле схемы. Ошибки схемы выявляются при её загрузке с указанием поля (как сейчас).

| Опция | Смысл |
| --- | --- |
| `choices: [...]` | Допустимые значения; для `list[str]` проверяется каждый элемент |
| `pattern: regex` | Полное совпадение (`re.fullmatch`); для списков — `item_pattern` для элементов. Regex компилируется при загрузке схемы |
| `type: link`, `list[link]` | Строка-ссылка на другой ресурс: slug, составной IRI `префикс:имя` или абсолютный IRI. Валидируется как `str`, но помечает поле для проверки ссылок и экспорта |
| `on_create` | `today` или `now`, см. 4.5 |
| `description` | Уже есть; попадает в JSON Schema (5.7) |

**5.2 Ключи JSON-LD.** Ключи `@id`, `@type`, `@context` задаются через существующий `alias`, например `FieldSpec("doc_id", alias="@id")`. Ключи с `@` должны корректно читаться и записываться (в YAML их обязательно брать в кавычки; сериализатор ставит кавычки сам), это покрывается круговым тестом. Ключ `@context` в документе допустим как поле типа `dict` или `any` и переопределяет контекст схемы для этого документа.

**5.3 Секция `jsonld` файла схемы.** Необязательна: без неё JSON-LD-функции выключены. Синтетический пример:

```yaml
version: 1
extra: forbid
fields:
  id:       {alias: "@id", pattern: "note:[0-9]{4}"}
  kind:     {alias: "@type", default: Note}
  title:    {required: true, role: title, max_length: 200}
  status:   {required: true, choices: [draft, active, retired]}
  date:     {type: date, role: date}
  replaces: {type: "list[link]"}
  related:  {type: "list[link]"}
  tags:     {type: "list[str]", role: tags}
jsonld:
  context:                    # inline, путь к файлу в проекте или список
    "@vocab": "https://example.org/vocab#"
    note: "https://example.org/notes/"
    replaces: {"@id": "https://example.org/vocab#replaces", "@type": "@id"}
    related:  {"@id": "https://example.org/vocab#related",  "@type": "@id"}
    date: {"@id": "https://example.org/vocab#date", "@type": "http://www.w3.org/2001/XMLSchema#date"}
  base: "https://example.org/"
  id: "{base}{collection}/{slug}"   # используется, если нет поля с alias @id
  type: Note                        # @type по умолчанию
  content_term: null                # термин для тела документа; null — не выводить
```

И документ к нему:

```markdown
---
"@id": note:0007
"@type": Note
title: Use plain files
status: active
date: 2026-10-01
replaces: [note:0003]
tags: [storage]
---
Body text.
```

**5.4 Эмиссия.** Документ превращается в объект JSON-LD по правилам:

- ключи — внешние (`alias`), значения — из проверенной модели; `None` и пустые значения не выводятся;
- `@context` берётся из схемы (или из документа); `@id` — значение поля с alias `@id`, иначе по шаблону `jsonld.id`; `@type` — поле с alias `@type`, иначе `jsonld.type`;
- тело выводится только при заданном `content_term` (Markdown как есть, HTML не выводится);
- даты в ISO 8601; порядок ключей: `@context`, `@id`, `@type`, затем по порядку схемы; никаких времён генерации, абсолютных путей и номеров строк.

Интерфейсы:

- Python: `document_to_jsonld(doc, collection) -> dict`, `collection_to_jsonld(collection) -> dict` (`@graph`, документы отсортированы по `@id`, затем по slug).
- HTTP (включается `jsonld_routes=True`, по умолчанию выключено): `GET {prefix}/{slug}.jsonld` и `GET {prefix}/index.jsonld`, `Content-Type: application/ld+json`; публичный вывод содержит только опубликованные документы.
- CLI: `python -m fastapi_blog export --collection NAME --format jsonld [--out FILE]`. С extra `jsonld` доступны также `--format expanded` и `--format nquads` (через `pyld`; вывод сортирован, пригоден для `git diff`).

**5.5 Контекст и безопасность.** По умолчанию контекст берётся только из inline-описания или файла внутри корня проекта. Удалённые контексты запрещены; включаются явным `allow_remote_contexts: [список URL]` и только при установленном extra `jsonld` (таймаут, лимит размера, без редиректов на другие хосты). Лимиты размера контекста и числа документов в `@graph` настраиваются. Ничего из контекста не исполняется.

**5.6 Контроль «потерянных терминов».** При разворачивании JSON-LD молча отбрасывает ключи, не определённые в контексте. Поэтому `check` (раздел 6) сообщает о ключе схемы, не покрытом контекстом ни термином, ни префиксом, ни `@vocab` (`strict_context: error`, `warn` или `off`, по умолчанию `error`). Статическая проверка (без `pyld`) разбирает inline или локальный контекст; при наличии `pyld` дополнительно разворачивается пробный документ. Контекст, который нельзя загрузить, даёт `undefined`, а не «ок».

**5.7 Дополнительно (SHOULD).**

- `python -m fastapi_blog schema --json-schema` печатает JSON Schema frontmatter из Pydantic-модели (`choices` → `enum`, `pattern`, описания).
- Роль `status` как обобщение `published`: список `published_values` в схеме определяет, какие документы публичны; одновременное задание ролей `published` и `status` — ошибка схемы.

**Критерии (C):**

1. Синтетическая коллекция из 5.3 (файлы `notes/0001-….md`) создаётся только файлами, `check` проходит.
2. Неверный `status`, неподходящий `@id` и поле вне контекста дают три отдельные диагностики.
3. Экспорт детерминирован: два запуска дают одинаковые байты, порядок файлов в ФС не влияет.
4. Круговой тест ключей с `@`.
5. Существующие схемы из `tests/examples` работают без изменений.

## 6. Проверки и CLI (фаза D)

**6.1 `python -m fastapi_blog check [--collection NAME] [--json] [--fail-on error|warning]`.** Проверяет: разбор файла, схему, дубликаты уникальных ключей (6.4), ссылки (`check.links: off|warn|error`, по умолчанию `off`; ссылка разрешается по полю с alias `@id` или по slug в той же коллекции; абсолютные IRI вне коллекции пропускаются), контекст (5.6), внешние проверки (6.2). Коды выхода: `0` — чисто; `1` — есть находки уровня не ниже `--fail-on` (по умолчанию `error`); `2` — находок нет, но что-то нельзя было проверить (`undefined`); `64` — ошибка использования или конфигурации. `undefined` никогда не сводится к «чисто», но находка приоритетнее неопределённости. Вывод детерминирован; `--json` — машинный формат.

**6.2 Внешние проверки (`validators`).** В конфигурации коллекции — список проверок: Python-callable `(doc, ctx) -> list[Issue]` или команда.

```yaml
validators:
  - name: lint
    argv: ["markdownlint", "{path}"]       # список, без shell
    exit_map: {0: ok, 1: error, 2: undefined}
    unavailable: undefined                 # команда не найдена или таймаут
    timeout: 20
    blocking: [error, undefined]           # что блокирует запись через API и админку
```

Подстановки: `{path}` (формирует хранилище: путь файла относительно корня проекта), `{slug}`, `{collection}` и `{field.NAME}` (скалярное поле frontmatter). Значения `{slug}`, `{collection}`, `{field.NAME}` обязаны соответствовать `[A-Za-z0-9._:-]+`, иначе проверка завершается ошибкой и команда не запускается. Запуск без shell, `cwd` — корень проекта, окружение — белый список, вывод ограничен по размеру и попадает в диагностику как текст. Команды берутся только из конфигурации, никогда из запроса.

**6.3 Запись с проверкой.** Для API и админки: под блокировкой коллекции записать новый вариант, выполнить блокирующие проверки на результате; при блокирующем исходе вернуть прежнее содержимое (или удалить созданный файл) и ответить HTTP 422 с телом `issues`. Ограничение (документировать): промежуточное состояние на диске видно другим читателям; проверка во временной копии вне этого ТЗ.

**6.4 Нумерация и уникальность (SHOULD).** `slug_template: "{seq:04d}-{title_slug}"` и `unique: [seq]`: следующий номер вычисляется под блокировкой по существующим именам файлов (регулярное выражение выводится из шаблона); второй документ с тем же `seq` — конфликт. Правило получения `title_slug` простое и задокументированное. Для файлов, созданных вручную, дубликаты находит `check`.

**6.5 Событие изменения (MAY).** Хук `on_change(event)` (`created`, `updated`, `deleted`; slug, etag, пользователь) без хранения журнала.

**Критерии (D):** коды выхода `0/1/2/64` покрыты тестами; внешняя команда даёт исходы `ok`, `error`, `undefined`, `unavailable`, включая таймаут; значение вроде `a;rm` в подстановке отклоняется, команда не запускается; блокирующий исход возвращает файл в прежнее состояние.

## 7. Админка и безопасность (extra `admin`, фаза E)

1. `authorize(request, resource, action) -> bool` — единая точка проверки прав; используется во всех представлениях админки (флаги `can_create`, `can_edit`, `can_delete` и серверная проверка) и в REST API. По умолчанию — запрет. Функцию можно заменить своей.
2. Роли `admin`, `editor`, `viewer` реально применяются. Тест: `viewer` не может записать ни через админку, ни через API (403).
3. Нет учётных данных по умолчанию: без заданных пароля и секрета сессии `add_admin_to_app` и `setup_fastapi_blog` поднимают ошибку конфигурации. Явный `insecure_dev=True` возвращает прежнее поведение с громким предупреждением. Слабый секрет (короче 32 символов или из списка известных) без `insecure_dev` — ошибка, а не предупреждение.
4. Сравнение секретов — `secrets.compare_digest`. Cookie сессии: `SameSite=Lax` как минимум, `https_only` настраивается; запросы записи с cookie проверяют `Origin` и `Host`.
5. Админка сохраняет через сервисный слой напрямую (без HTTP-вызова собственного API). Форма строится из схемы: `choices` — select, `pattern` — подсказка и валидация, `link` — текстовое поле; показывает диагностику проверок и конфликт `etag`.
6. Показ диффа перед сохранением и история изменений — вне объёма (MAY).

**Критерии (E):** тесты прав на все роли и действия; запуск без пароля падает с понятной ошибкой; форма для схемы из 5.3 показывает select для `status`.
