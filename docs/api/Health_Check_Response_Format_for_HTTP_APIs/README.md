# Формат ответа health-check эндпоинта для HTTP API

Для эндпоинта проверки состояния сервиса (`/health`, `/api/health`, или `/api/<version>/health`) **не существует утверждённого RFC**, но есть [черновик IETF — draft-inadarei-api-health-check](https://datatracker.ietf.org/doc/draft-inadarei-api-health-check/), который де-факто стал отраслевым ориентиром: на его терминологию и алиасы статусов прямо ссылаются такие фреймворки, как Spring Boot Actuator и Node.js Terminus.

Структура, названия полей и HTTP-семантика ниже приведены в соответствие с последней и единственной актуальной редакцией черновика (**draft-06**, октябрь 2021). Нормативные формулировки самого черновика размечены по шкале MUST/SHOULD/MAY ниже — она соответствует уровням из RFC 2119, на которые сам черновик прямо ссылается.

### 📄 Статус документа-первоисточника

* Трек — **Informational**, не Standards Track — черновик никогда не претендовал на статус обязательного стандарта.
* Последняя редакция (`-06`) истекла **19 апреля 2022 года** и с тех пор не обновлялась и не была продвинута до RFC.
* Формально черновик не является действующим стандартом, но остаётся самым подробным и широко цитируемым описанием формата.

### 🎚 Шкала обязательности

* **MUST** — обязательное правило. Нарушение ломает согласованность системы между проектами.
* **SHOULD** — рекомендация по умолчанию. Есть конкретная причина отклониться — отклоняйся, но осознанно и зафиксировав.
* **MAY** — опционально, включается по потребности проекта. Отсутствие MAY-элемента — не нарушение.

Ниже это применяется к двум источникам правил: тем, что прямо задаёт сам черновик IETF (помечены как «из спецификации»), и тем, что добавлены как инженерная практика поверх него (помечены как «практика проекта») — их обязательность вы определяете сами, шкала для них — рекомендация к использованию в вашей команде.

### 🧭 Дизайн эндпоинта: liveness, readiness и базовый путь *(практика проекта)*

Разделение на несколько эндпоинтов не входит в черновик — это общепринятая эксплуатационная практика (в основном из Kubernetes), которая хорошо сочетается с форматом ответа выше. Ниже — зафиксированная для этого проекта структура путей.

| Путь | Роль | Тело ответа | HTTP-код |
|---|---|---|---|
| `GET /api/<version>/health` | **Base Probe** — полный draft-06-совместимый отчёт для мониторинга/observability | Расширенная структура, `checks` по всем отслеживаемым компонентам | по правилам из раздела «HTTP статус-коды» |
| `GET /api/<version>/health/live` | **Liveness** — «жив ли процесс» | Минимальная структура `{"status": "pass"}` | Всегда `200 OK`, если сервер вообще отвечает (если процесс завис — ответа не будет вовсе, это и есть сигнал для K8s/Docker на перезапуск) |
| `GET /api/<version>/health/ready` | **Readiness** — готовность принимать трафик: БД, критичные зависимости | Минимальная или расширенная структура, `checks` — только критичные компоненты | `pass` → `200 OK` (в трафик), `fail` → `503` (убрать из балансировки, **не** перезапуск) |

* **MUST** *(зафиксированное решение проекта)* — каждый сервис в этой архитектуре предоставляет все три пути.
* **SHOULD** — `live` не обращается ни к одной внешней зависимости (БД, кэш, очереди и т.д.). Иначе он теряет смысл как liveness-проверка: деградация соседнего сервиса начнёт вызывать ложные рестарты вместо того, чтобы просто вывести инстанс из балансировки через `ready`.
* **SHOULD** — `ready` переиспользует ту же логику проверок, что и base, но ограничивается критичными зависимостями и не обязан отдавать детализацию не хуже base — балансировщику важен только код ответа.
* **MAY** — `live` и `ready` тоже возвращают draft-06-совместимое тело (`{"status": ...}`), а не произвольный формат — ради единообразия с остальными эндпоинтами.

### Реализация в fastapi-blog

При использовании `add_blog_to_fastapi()` или `setup_fastapi_blog()` все три
пробы регистрируются автоматически и отображаются в `/docs` как операции
OpenAPI с ответами `application/health+json`. Отключать их через
`health_routes=False` следует только тогда, когда приложение самостоятельно
предоставляет совместимые health endpoints. Пути реализации зафиксированы
под `/api/v1`.

> ⚠️ **Компромисс, который стоит явно зафиксировать**: все три пути живут под `/api/<version>`. Это самый простой вариант (единое пространство путей, общая конфигурация gateway/auth), но версионирование инфраструктурных проб создаёт риск: с появлением `/api/v2` конфигурацию `livenessProbe`/`readinessProbe` в манифестах и настройках балансировщика придётся синхронно обновлять для всех сервисов, хотя сама механика health-check от версии бизнес-API не зависит. Разбор альтернатив — в сопроводительном сообщении.

### 🔤 Media type и content negotiation

```http
GET /health HTTP/1.1
Host: api.example.com
Accept: application/health+json

HTTP/1.1 200 OK
Content-Type: application/health+json
Cache-Control: max-age=60
```

* **SHOULD** *(из спецификации)* — публиковать ответ с `Content-Type: application/health+json` — это зарегистрированный media type черновика.
* **MAY** *(практика проекта, документированное отклонение от SHOULD)* — отдавать `application/json` вместо этого, если аудитория эндпоинта — разнородные системы мониторинга, часть которых не умеет работать с кастомным media type. Если выбираете этот путь — зафиксируйте это как осознанное отклонение (например, в README сервиса), а не оставляйте как случайность.

### 📐 Базовая структура (минимальный ответ)

* **MUST** *(из спецификации)* — ответ обязан содержать поле `status`. Это единственное обязательное поле формата.

```json
{
  "status": "pass"
}
```

### 🏗 Расширенная структура (все поля верхнего уровня)

```json
{
  "status": "pass",
  "version": "1.2.3",
  "releaseId": "1.2.3-4",
  "notes": [],
  "output": "",
  "serviceId": "f03e522f-1f44-4062-9b55-9587f91c9c41",
  "description": "Health check основного API сервиса",
  "checks": { },
  "links": {
    "about": "https://api.example.com/about",
    "self": "https://api.example.com/health"
  }
}
```

### 📝 Описание полей верхнего уровня

* **`status`** — **MUST** присутствовать. Значение регистронезависимо.
    * **SHOULD** использовать `"pass"` / `"fail"` / `"warn"` как основные значения.
    * **MAY** использовать алиасы для совместимости с конкретными экосистемами: `"ok"`/`"up"` вместо `"pass"` (Node Terminus / Spring Boot), `"error"`/`"down"` вместо `"fail"` (Node Terminus / Spring Boot). У `"warn"` алиасов не определено.
* **`version`, `releaseId`, `notes`, `serviceId`, `description`, `checks`, `links`** — все **MAY**: поле опционально, его отсутствие не является нарушением формата.
    * Уточнение по смыслу: `version` — публичная версия API (меняется редко), `releaseId` — идентификатор конкретной сборки/деплоя (меняется часто, даже когда `version` стабилен).
* **`output`** — **MAY** присутствовать как поле, но:
    * **SHOULD** — при `status: "pass"` поле следует опускать (сырой текст ошибки не нужен, когда ошибки нет).

### 🧩 Объект `checks`: как он устроен на самом деле

`checks` — это объект (словарь), а не массив: каждый ключ — отдельная зависимость/метрика, значение — **массив** объектов-наблюдений (массив обязателен даже для одного узла — ради единообразия структуры между сервисами с одной нодой и с несколькими).

Ключ имеет вид `"{componentName}:{measurementName}"`:

* **MUST** — ни `componentName`, ни `measurementName` не должны содержать символ `:` (зарезервирован как разделитель).
* **SHOULD** — использовать массив из одного элемента для однонодового компонента, а не голый объект — ради единообразия со случаем нескольких нод.
* **SHOULD** — ключ должен быть уникален в пределах объекта `checks`.
* **MAY** — использовать составной ключ `component:measurement`; допустим и ключ из одной части (например, просто `"uptime"`, без имени компонента) — обе формы валидны.
* **SHOULD** — для `measurementName` использовать одно из предопределённых значений (`utilization`, `responseTime`, `connections`, `uptime`) или общепринятый термин; при выборе полностью произвольного имени клиенты, не знающие вашей семантики, не смогут его интерпретировать автоматически — это не нарушение формата, но снижает интероперабельность.

Каждый элемент массива-значения:

* **SHOULD** — содержать хотя бы один ключ (пустой объект бессмысленен).
* **`componentId`** — **MAY**. Нужен, если у зависимости несколько нод: **MAY** быть несколько объектов с одинаковым `componentId`, если они относятся к разным нодам одного логического компонента.
* **`componentType`** — **MAY** как поле, но **SHOULD** присутствовать, если задан `componentName` (часть ключа). Значение: `component` / `datastore` / `system`, общепринятый термин, либо URI.
* **`observedValue`** — **MAY**.
* **`observedUnit`** — **MAY** как поле, но **SHOULD** присутствовать, если задан `observedValue` — иначе число неинтерпретируемо (`240` — это мс, проценты, штуки?).
* **`status`** — **MAY**, та же семантика, что у корневого `status`.
* **`affectedEndpoints`** — **MAY** как поле, но **SHOULD** опускаться при `status: "pass"` этой проверки.
* **`time`** — **MAY**. ISO 8601, время снятия показания (значение может быть кэшировано и не отражать «прямо сейчас»).
* **`output`** — **MAY** как поле, но **SHOULD** опускаться при `status: "pass"`.
* **`links`** — **MAY**.
* Произвольные дополнительные ключи — **MAY** присутствовать; потребители, которые их не понимают, **MAY** их игнорировать (то есть игнорирование неизвестных ключей — тоже допустимое поведение, а не ошибка).

### 🚦 HTTP статус-коды

| `status` | Требование | Уровень |
|---|---|---|
| `pass` | HTTP-код в диапазоне 2xx–3xx | **MUST** |
| `warn` | HTTP-код в диапазоне 2xx–3xx (даже при наличии проблем — не 4xx/5xx) | **MUST** |
| `warn` | Дополнительные детали через `checks`/`notes`/`output` | **SHOULD** |
| `fail` | HTTP-код в диапазоне 4xx–5xx | **MUST** |

* **SHOULD** *(клиентское поведение из спецификации)* — балансировщики, service discovery и подобные инструменты должны трактовать HTTP-код health-эндпоинта как код здоровья всего компонента целиком, а не только самого эндпоинта.
* **MAY** *(практика проекта)* — конкретный код внутри диапазона: обычно `200 OK` для `pass`/`warn` и `503 Service Unavailable` для `fail`, но это выбор реализации, а не требование спецификации.

### ⏱ Кэширование и ссылки

* **SHOULD** *(из спецификации)* — назначать ответу время жизни через `Cache-Control: max-age=...` или `ETag`, чтобы мониторинг не опрашивал эндпоинт слишком часто.
* **MUST NOT** *(клиентское поведение из спецификации)* — клиенты не должны считать ссылки из `links` валидными за пределами времени жизни ответа; `404` по такой ссылке — повод запросить свежий health-check, а не ошибка клиента.

### 🔒 Безопасность *(практика проекта, дополняет раздел Security Considerations черновика)*

Черновик прямо предупреждает: детальная информация в ответе может использоваться для разведки при атаке, и в некоторых случаях эндпоинт может требовать аутентификации. С учётом конкретных путей выше это разбивается так:

* **MUST** — `/api/<version>/health/live` и `/api/<version>/health/ready` остаются доступны без аутентификации. Их дёргают kubelet и балансировщик — они обычно не умеют проходить auth, и гейтить эти пути — значит сломать сами пробы.
* **SHOULD** — при этом `/ready` не обязан отдавать детальный `checks` в теле: двух состояний (`pass`/`fail`) достаточно балансировщику, а подробности о топологии можно не публиковать даже на незащищённом пути.
* **SHOULD** — `/api/<version>/health` (base, полный `checks` по всем компонентам, включая некритичные) — единственный из трёх путей, для которого стоит рассматривать ограничение доступа: аутентификацию, RBAC или доступность только из внутренней сети/service mesh. Именно он реально раскрывает внутреннюю топологию (БД, число нод, `componentId`).
* **MAY** — вместо аутентификации ограничиться сетевым уровнем: `base` доступен только из VPN/service mesh, наружу через reverse proxy отдаётся только `status`.

### 💡 Итоговый чек-лист

* **MUST** — поле `status` присутствует и имеет значение `pass`/`fail`/`warn` (или согласованный алиас).
* **MUST** — HTTP-код ответа соответствует диапазону, требуемому значением `status`.
* **MUST** — `componentName`/`measurementName` в ключах `checks` не содержат `:`.
* **MUST** — сервис предоставляет все три пути: `/api/<version>/health` (base), `/api/<version>/health/live`, `/api/<version>/health/ready`.
* **SHOULD** — `checks` — объект вида `{"компонент:метрика": [...]}`, а не массив.
* **SHOULD** — `output`/`affectedEndpoints` (и на верхнем уровне, и внутри `checks`) опускаются при `status: "pass"`.
* **SHOULD** — ответу назначен `Cache-Control`/`ETag`.
* **SHOULD** — детализация (`checks`) видна только на `/api/<version>/health`; `/live` и `/ready` остаются публичными и без неё.
* **MAY** — `version` отделён от `releaseId`; используется `application/health+json` вместо `application/json`; заданы `links`.
